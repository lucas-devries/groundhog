## Antwort

**Beide Projekte schotten einen Bypass-Run ab, indem der ganze Claude-Prozess in einer fremden Grenze läuft; keines verlässt sich auf Claudes eigene Bash-Sandbox.** Ralph (Pocock) nutzt dafür ausschließlich `docker sandbox run claude`. `sandcastle` verlangt bei jedem `run()` ausdrücklich einen Sandbox-Provider; `init` empfiehlt den nativen des Betriebssystems (`seatbelt()` auf macOS, `bwrap()` auf Linux), Docker, Podman und Cloud-VMs (E2B, Modal, Sprites, Vercel, Daytona) sind Alternativen, `noSandbox()` ist ein bewusstes Opt-out.

**Netz ist in beiden Projekten offen**, bei `sandcastle` nativ sogar inklusive `localhost` des Hosts; eine Egress-Sperre gibt es nur bei Docker Sandboxes (deny-by-default per Policy), in Anthropics Referenz-Devcontainer (iptables-Allowlist) und in Anthropics Sandbox-Runtime `srt`. **Secrets:** `sandcastle` versteckt die Logins im Home-Verzeichnis (`~/.claude`, `~/.config/gh`), reicht aber `CLAUDE_CODE_OAUTH_TOKEN` und `GH_TOKEN` aus `.sandcastle/.env` als Klartext-Umgebungsvariablen in den Sandbox; der Agent kann sie lesen und über das offene Netz verschicken. Docker Sandboxes und Anthropics Cloud-Sessions halten Token dagegen außerhalb der Grenze und setzen sie über einen Proxy ein.

**Für den Start ohne Sandbox** sagen alle drei dasselbe: kein Bypass. Anthropic: Bypass „only in isolated environments like containers, VMs, or dev containers without internet access“; ohne Isolation lieber Auto-Mode (Klassifizierer), der laut Doku keine Grenze braucht. `sandcastle`: `noSandbox()` ist Opt-in, und für unsandboxed Runs empfiehlt der Code `permissionMode: "auto"` statt Bypass. Pocock: ohne Sandbox nur HITL (`claude --permission-mode acceptEdits`, Mensch schaut zu); für AFK sind Sandboxes „essential insurance“.

### Docker Sandboxes (was Ralph tatsächlich abschottet)

Die aktuelle Doku beschreibt das Produkt unter dem CLI `sbx`, nicht unter `docker sandbox run`. Dass Pococks `docker sandbox` (Docker Desktop 4.50) heute dieselben Eigenschaften hat, ist **[nicht verifiziert]**; Pocock selbst spricht von einem „container“, die Doku von microVMs.

- **Grenze:** eine microVM pro Sandbox, eigener Kernel, eigener Docker-Daemon, kein Zugang zum Host-Daemon; im VM hat der Agent `sudo` ([Security model](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/sandboxes/security/_index.md)).
- **Bypass ist Standard:** „Without extra args, the sandbox runs: `claude --dangerously-skip-permissions`“ ([agents/claude-code.md](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/sandboxes/agents/claude-code.md)).
- **Dateien:** Standard ist der direkte Mount des aktuellen Verzeichnisses, read-write, inklusive Git-Hooks und Build-Skripten; Docker warnt ausdrücklich, dass Hooks in `.git/` nicht in `git diff` auftauchen. Optional `--clone` (Repo read-only, Agent arbeitet auf privatem Klon) oder ganz ohne Mount ([defaults.md](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/sandboxes/security/defaults.md), [Security model](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/sandboxes/security/_index.md)). `~/.claude` des Hosts wird nicht übernommen.
- **Netz:** ausgehendes TCP blockiert, außer eine Regel erlaubt das Ziel; UDP und ICMP aus. Beim ersten Start fragt das CLI nach einem Preset; empfohlen ist „Balanced“ (gängige Dev-Dienste erlaubt), „Locked Down“ verlangt für jedes Ziel eine Regel ([defaults.md](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/sandboxes/security/defaults.md), [get-started.md](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/sandboxes/get-started.md)). Die Defaults enthalten breite Wildcards, und die Hostnamen-Filter lassen sich über gemeinsame IP-Adressen umgehen ([network-rules.md](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/governance/local/network-rules.md)).
- **Secrets:** Ohne `sbx secret` oder Env-Variable gibt es keine Credentials im Sandbox. Gesetzte Secrets setzt ein Proxy auf dem Host in die HTTP-Header ein; der Agent sieht nur einen Platzhalter. Ein `github`-Secret (`sbx secret set github --command 'gh auth token'`) macht `gh` im Sandbox nutzbar und gilt für `api.github.com`, `github.com` u. a. SSH-Agent-Forwarding ist standardmäßig an ([credentials.md](https://github.com/docker/docs/blob/e9df242357953de74c7ae200d17f3ec6dc9d6f0b/content/manuals/ai/sandboxes/configuration/credentials.md)). Claude-Abo-Login geht per `/login` im Sandbox bzw. Host-OAuth, dessen Token laut Doku den Sandbox nicht betritt.

## `sandcastle`

### Was Standard ist

- **Ein Sandbox ist Pflicht:** `sandbox` ist bei `run()` „**Required.**“, es gibt keinen Standard-Provider ([run.md, Z. 28](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/run.md?plain=1#L28)). Nur `wt.interactive()` fällt ohne Angabe auf `noSandbox()` zurück ([sandbox-providers.md, Z. 17](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/sandbox-providers.md?plain=1#L17)).
- **Empfehlung bei `init`:** der native Provider des OS, vorausgewählt und als „(recommended)“ markiert; Docker und Podman folgen ([init.md, Z. 16](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/init.md?plain=1#L16); [InitService.ts, Z. 866–883](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/InitService.ts#L866-L883)).
- **Bypass ist Standard:** jeder Agent-Aufruf in `run()` baut `--dangerously-skip-permissions` ein ([Orchestrator.ts, Z. 170–175](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/Orchestrator.ts#L170-L175)), auch bei `noSandbox()`. Nur `interactive()` lässt das Flag weg, wenn kein Sandbox da ist ([interactive.ts, Z. 412](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/interactive.ts#L412)). Ein gesetztes `permissionMode` ersetzt das Flag ([AgentProvider.ts, Z. 1723–1760](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/AgentProvider.ts#L1723-L1760)).
- **Claudes eigene Sandbox aus:** „The native sandbox is the containment layer, and Sandcastle already runs agents with their permission checks skipped, so turn off the agent's own sandboxing.“ Im `seatbelt()` kann Claude seine eigene Seatbelt-Sandbox gar nicht starten, weil macOS keine Verschachtelung erlaubt ([sandbox-providers.md, Z. 106–108](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/sandbox-providers.md?plain=1#L106-L108)).
- **Git-Härtung bei allen Bind-Mount-Providern:** `.git/config`, `.git/hooks`, `.git/info` und die Worktree-Verwaltung sind read-only gemountet; die Git-Befehle, die Sandcastle auf dem Host ausführt, ignorieren Repo-Hooks und Repo-Config, die Programme nennt ([branch-strategies.md, Z. 29–31](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/branch-strategies.md?plain=1#L29-L31)).

### Native Provider: `seatbelt()` und `bwrap()`

Quelle, wo nicht anders angegeben: [sandbox-providers.md, Z. 48–108 und 184–195](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/sandbox-providers.md?plain=1#L48-L108).

- **Dateien:** schreibbar nur Repo bzw. Worktree, die gemounteten Git-Verzeichnisse, ein privates Temp und ein privates Home (beim Schließen gelöscht). Home, SSH-Keys, Agent-Logins und andere Repos sind verborgen. Lesbar ist die Toolchain: jedes Verzeichnis im Host-`PATH` plus Installationsordner von dort verlinkter Programme, aber nie das Home oder ein Vorfahr davon.
- **Env:** nur die Variablen, die Sandcastle übergibt, plus `PATH`, `HOME`, `TMPDIR` (`bwrap` mit `--clearenv`, [bwrapSandbox.ts, Z. 224–237](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/bwrapSandbox.ts#L224-L237)).
- **Netz:** „Open, including your host's localhost.“ `bwrap` läuft mit `--unshare-all --share-net` ([bwrapSandbox.ts, Z. 234–235](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/bwrapSandbox.ts#L234-L235)), das Seatbelt-Profil enthält `(allow network*)` ([seatbeltProfile.ts, Z. 182](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/seatbeltProfile.ts#L182)). Es gibt keine Option, das Netz zu sperren.
- **Kein root:** `sudo: true` wird abgelehnt.
- **Fällt nie stillschweigend zurück:** Ist das Werkzeug nicht nutzbar, wirft der Konstruktor `NativeSandboxUnavailableError`, bevor ein Worktree existiert, „and it never falls back to running the agent unsandboxed“. Auf Ubuntu ab 24.04 blockiert AppArmor die nötigen User-Namespaces; die Doku liefert dafür ein AppArmor-Profil.
- **Was die native Sandbox nicht abdeckt (laut Doku):** Kernel-Ausbrüche („`bwrap()` is about as strong as a runc container“, „`seatbelt()` is weaker than Docker Desktop“), Dienste auf `127.0.0.1` des Hosts, die Prozessliste unter macOS (Seatbelt hat keinen PID-Namespace) und Prozesse, die sich unter macOS per `setsid` aus der Prozessgruppe lösen; die überleben `close()`. Unter `seatbelt()` ist der macOS-Schlüsselbund nicht zuverlässig verborgen. Gedacht ist die native Sandbox gegen „accidents and prompt-injection attacks“.

### Secrets und `gh`-Token

- `.sandcastle/.env` ist die einzige Quelle: Nur dort deklarierte Schlüssel werden aufgelöst (Wert aus der Datei, sonst aus `process.env`); die `.env` im Repo-Root zählt nicht ([EnvResolver.ts, Z. 61–85](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/EnvResolver.ts#L61-L85)). Die Werte landen als Umgebungsvariablen im Sandbox (`-e` bei Docker, [DockerLifecycle.ts, Z. 125–128](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/DockerLifecycle.ts#L125-L128)); die Doku warnt selbst: „the keys declared there are forwarded into the sandbox“ ([sandbox-providers.md, Z. 112](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/sandbox-providers.md?plain=1#L112)).
- Für Claude: `CLAUDE_CODE_OAUTH_TOKEN` (aus `claude setup-token`) oder `ANTHROPIC_API_KEY` in `.sandcastle/.env` ([getting-started.md, Z. 38](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/getting-started.md?plain=1#L38)).
- Für GitHub Issues: „put a `GH_TOKEN` in `.sandcastle/.env`, because the sandbox hides your host's `gh` login“ ([init.md, Z. 18](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/init.md?plain=1#L18); [InitService.ts, Z. 751 und 928](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/InitService.ts#L751)). Welche Rechte das Token haben soll, sagt die Doku nicht.
- **[Schluss]** Weil das Netz offen ist und die Token im Klartext in der Umgebung stehen, kann ein per Prompt-Injection gesteuerter Agent beide Token abziehen. Die Git-Identität des Hosts wird hineinkopiert, Commits tragen also den Namen des Nutzers ([sandbox-providers.md, Z. 54](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/sandbox-providers.md?plain=1#L54)).

### Ohne Sandbox

- `noSandbox()` heißt in der Doku „opt in to running the agent directly on the host when isolation is undesired“ ([sandbox-providers.md, Z. 3](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/sandbox-providers.md?plain=1#L3)).
- Für unsandboxed Runs empfiehlt `sandcastle` `permissionMode: "auto"`: „Use `"auto"` for AI-mediated per-tool approve/deny on unsandboxed host runs“ ([AgentProvider.ts, Z. 1723–1727](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/AgentProvider.ts#L1723-L1727); [agent-providers.md, Z. 29](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/docs/guide/agent-providers.md?plain=1#L29)).
- Achtung: Ohne `permissionMode` läuft `run({ sandbox: noSandbox() })` trotzdem mit Bypass direkt auf dem Host (siehe oben, `Orchestrator.ts`). Der Kopfkommentar von [`no-sandbox.ts`](https://github.com/mattpocock/sandcastle/blob/1b380ca5e7a9fbece96c49d9edba264c1f512c4e/src/sandboxes/no-sandbox.ts#L1-L11) sagt das Gegenteil („Does not pass `--dangerously-skip-permissions`“); das stimmt nur für `interactive()`.

## Anthropic

- **Bypass nur mit Grenze um den ganzen Prozess:** „Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime, so that file tools, MCP servers, and hooks are also inside the boundary“, als Nicht-root ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments.md#how-isolation-relates-to-permission-modes)). Die Moduswahl-Tabelle sagt für „Run fully unattended“ mit `claude -p … --dangerously-skip-permissions`: „Required: a container, VM, or the sandbox runtime“ ([permission-modes](https://code.claude.com/docs/en/permission-modes.md#common-setups)). Strenger in der Warnung beim Modus selbst: „Only use this mode in isolated environments like containers, VMs, or dev containers without internet access“ ([permission-modes](https://code.claude.com/docs/en/permission-modes.md#skip-all-checks-with-bypasspermissions-mode)).
- **Claudes eingebaute Bash-Sandbox reicht nicht:** Sie umfasst nur Shell-Befehle; Read/Edit/WebFetch, Hooks, MCP-Server und Plugin-Monitore laufen außerhalb, „so it is not sufficient for fully unattended runs in either mode“ ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments.md#how-isolation-relates-to-permission-modes); [sandboxing](https://code.claude.com/docs/en/sandboxing.md#what-runs-outside-the-sandbox)). Sie ist standardmäßig aus; wenn an, sind Lesezugriffe auf fast die ganze Maschine erlaubt (auch `~/.ssh`), Netz geht nur über einen Proxy mit anfangs leerer Allowlist, und Umgebungsvariablen samt Secrets werden vererbt ([sandboxing](https://code.claude.com/docs/en/sandboxing.md#what-the-sandbox-restricts)). Mit `sandbox.credentials` lassen sich Variablen wie `GH_TOKEN` sperren oder maskieren (Proxy setzt den echten Wert nur für erlaubte Hosts ein, verlangt TLS-Terminierung); `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` entfernt Credentials aus allen Subprozessen ([sandboxing](https://code.claude.com/docs/en/sandboxing.md#protect-credentials)).
- **Sandbox-Runtime `srt`** (`@anthropic-ai/sandbox-runtime`, Beta): dieselbe Seatbelt-/bubblewrap-Technik um den ganzen Claude-Prozess. Standard: Netz zu, Schreiben nur in wenige Runtime-Pfade; man muss Projektverzeichnis, `~/.claude`, `~/.claude.json`, Temp sowie `api.anthropic.com` (und für Abo-Login `claude.ai`, `platform.claude.com`) freigeben. Ohne Konfiguration verweigert `.git/hooks`, `.git/config`, `.mcp.json`, `.claude/commands`, `.claude/agents` und Shell-Startdateien das Schreiben; unter Linux nur für das, was beim Start existiert ([sandbox-environments, „Sandbox runtime“](https://code.claude.com/docs/en/sandbox-environments.md#sandbox-runtime)).
- **Dev-Container:** Referenz mit Nicht-root-User `node`, Default-Deny-Firewall per iptables und Allowlist (GitHub-IP-Bereiche aus `api.github.com/meta`, `registry.npmjs.org`, `api.anthropic.com`, `sentry.io`, `statsig.com` u. a.; DNS, SSH und das Host-Netz bleiben offen), dafür `NET_ADMIN`/`NET_RAW` ([`init-firewall.sh`](https://github.com/anthropics/claude-code/blob/ce09c2ef4214e9db7bdf0caf5581701001113c8c/.devcontainer/init-firewall.sh), [`devcontainer.json`](https://github.com/anthropics/claude-code/blob/ce09c2ef4214e9db7bdf0caf5581701001113c8c/.devcontainer/devcontainer.json)). Die Doku warnt: „When executed with `--dangerously-skip-permissions`, dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`“; keine Host-Secrets wie `~/.ssh` mounten, „prefer repository-scoped or short-lived tokens“ ([devcontainer](https://code.claude.com/docs/en/devcontainer.md)).
- **VM:** stärkste Trennung; Docker Sandboxes wird ausdrücklich als microVM-Option genannt ([sandbox-environments, „Virtual machine“](https://code.claude.com/docs/en/sandbox-environments.md#virtual-machine)).
- **Cloud-Sessions:** Anthropic-VM, Netz-Allowlist per Proxy, GitHub-Token bleibt auf Anthropics Servern, im VM nur ein kurzlebiges, auf die Session begrenztes Credential; der Proxy lehnt Branch-Löschungen und Tag-Pushes ab ([security](https://code.claude.com/docs/en/security.md)). Bypass ist dort nicht verfügbar ([permission-modes](https://code.claude.com/docs/en/permission-modes.md)). Für groundhog als lokales CLI kein Weg.
- **Ohne Sandbox:** Auto-Mode „is not required the way it is for `--dangerously-skip-permissions`“; ein Klassifizierer prüft jede Aktion, eine Grenze ist dann nur zusätzliche Verteidigung ([sandbox-environments](https://code.claude.com/docs/en/sandbox-environments.md#how-isolation-relates-to-permission-modes)). Der Klassifizierer blockiert unter anderem das Starten einer autonomen Agent-Schleife ohne Sandbox mit `--dangerously-skip-permissions` ([permission-modes, „What the classifier blocks by default“](https://code.claude.com/docs/en/permission-modes.md#what-the-classifier-blocks-by-default)).
- Bypass-Root-Sperre und `IS_SANDBOX=1`: siehe #3.

## Was groundhog daraus ziehen kann (für #6)

**[Schluss]** Folgerungen, keine Entscheidungen:

1. **Die Grenze muss um den ganzen `claude -p`-Prozess liegen**, nicht nur um Bash. Das sagen Anthropic, `sandcastle` und Pocock übereinstimmend. Claudes eingebaute Bash-Sandbox genügt nicht.
2. **Das Netz ist die offene Flanke.** `sandcastle` und Docker-Standard lassen es offen; damit sind alle Token im Sandbox exfiltrierbar. Abhilfe in den Quellen: Egress-Allowlist (Devcontainer-Firewall, `srt`, Docker Sandboxes) oder Token gar nicht in den Sandbox geben.
3. **`gh` braucht der Run eigentlich nicht.** In groundhog liest und schreibt die Engine den Tracker (#8: Frontier, Assignee, Schließen). Ein Run braucht dann nur Git ohne Push-Recht und das Claude-Token. Das ist strenger als Ralph und `sandcastle`, die dem Agent das Schließen überlassen.
4. **Git-Interna schützen** (`.git/hooks`, `.git/config` read-only), weil die Engine nach dem Run auf dem Host Git ausführt; `sandcastle` und `srt` tun das, Docker Sandboxes im Direktmodus und der Devcontainer nicht.
5. **Ohne Sandbox kein Bypass.** Falls v1 einen Start ohne Sandbox zulässt, dann mit `--permission-mode auto` (Anthropic und `sandcastle` einig) und mit dem Wissen, dass ein Klassifizierer keine Grenze ist.
